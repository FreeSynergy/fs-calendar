# fs-calendar – Design

`fs-calendar` is the calendar program of FreeSynergy. This repo holds the **program core** (`crates/fs-calendar-core`, no GUI), the **server** (`crates/fs-calendar-server`, the contract over a Unix socket), the **task adapter** (`crates/fs-calendar-tasks`) and its frontend (`crates/fs-calendar-app`).
Events are **JSCalendar 2.0** objects (`draft-ietf-calext-jscalendarbis-22`) inside AS2 envelopes stored through
`fs-objects` (ADR 0014, 0019, 0020). Every program is at least a workbench (ADR 0037); the window is the generated admin screen over the `Event` description plus the calendar grid component of `fs-components` (ADR 0065, 0066); `fs-calendar-app` connects them to the core and knows no render code.

## State

Version 0.0.3 (branch `r1-admin`, not tagged): the type description of `Event`, `Events.types`, `EventBackend` and the admin window with the calendar grid (section "Admin window" below, with Unsupported and the temporary duplication). The rows below describe the core and the server, which did not change; older statements about the workbench window are history (tag `v0.0.2`).

Version 0.8.0 (branch `calendar-no-tasks-core`, not tagged; merged with `main`, which adds `fs-calendar-cli` and the patched `blinc_app`; `fs-tasks` pins are v0.9.0): **`fs-calendar-core` no longer depends on `fs-tasks-core`** (or any task crate; `cargo tree -p fs-calendar-core` has no `fs-tasks`, and `tests/tasks.rs` reads the manifest to keep it so). The core talks to the task program through two small traits (interface segregation, `src/tasks/`): `TasksInWindow` (`due_between(from, to)`, the one question the view asks) and `TaskIntake` (`import_ics(text)` and `forward(uid, jscalendar)`, the `uid` **as written**: the task program keeps and matches it as written, so a second import finds an upper-case UUID or a padded `uid` again, and `skipped` names it as written for a task found in a JSCalendar file; the answer is `Forwarded::{Created, Skipped, Refused}`, a refused task is lost alone: invalid, too large, or `tasks/conflict`, which is a `Skipped`; a task program that cannot be reached loses the tasks of the import, each named in `failed` (`uid: reason`, or `tasks of the text: reason` for the `.ics` text), and the events and the report stay; only a failure of the store ends the import with an error). A task travels as `DueTask { id, envelope, jscalendar: Value }`, the shape of `Task` in `tasks.capnp`, unread by the core; `Error::Tasks` carries a `TasksError` (text only). `CalendarRepo::with_tasks(Arc<dyn TasksInWindow>)` and `with_task_intake(Arc<dyn TaskIntake>)` replace `with_tasks(Arc<dyn TaskItems>)`; `Parsed::tasks` is a list of `TaskPart { uid, jscalendar }` (the text, not a `Task`), so the validation of a task is the task program's. New crate **`fs-calendar-tasks`**: `RpcTasks` implements both traits over the contract `tasks.capnp` (shared `Worker` of `fs-interfaces`, the contract in `remote.rs`; it knows no type of `fs-tasks-core`, which is not in its normal dependencies), and with the feature `local` `LocalTasks` puts a `TaskItems` held in this process behind the same traits. Tested against a real `fs-tasks-server` on a real socket with pages of two (`tests/rpc.rs`), with the same behaviour through `LocalTasks` (`tests/local.rs`), and in the core with a fake (`tests/common/fake_tasks.rs`). The **import is linear** (`repo/known.rs`): the known `uid`s are read once per import, in pages of 500 (type and context only, no index condition), and `store_new` stores without asking the store again; before, each part asked three times (part, `import_one`, `create_inner`) and the store answers a lookup by looking at every event. Measured by `tests/import_linear.rs`: the work asked of the store (calls, rows, and a charge of the stored events for each lookup by an index field) for 60 and 120 events is 181 and 361 (ratio 1.99; the old flow: 5 670 and 22 140, ratio 3.90, run against `main`). The set of `uid`s is held in memory for the length of one import. The import of the app (`import_file`) is one `import_ics` of the whole text (the old loop with one `import` per part read the known `uid`s again for every part: measured by the app's `tests/import_linear.rs`, 60 and 120 events cost 301 and 601, ratio 2.00; with the loop 2 070 and 7 740, ratio 3.74); only after a panic it falls back to part by part, and the `lost_zones` check reads the kept original of each created event. If the whole import fails with an error of the store (not a panic, and no longer a task program that is gone) it is reported as one failure, `the file: ...`, and the events stored before it exist but are not counted or checked for lost zones, because an `Err` carries no report (a known gap). After a panic the part-by-part fallback counts the events the first attempt had already stored as "already known" (skipped), not as created; the events are there, the count is low. The app (`fs-calendar-app`) still holds the task store in its own process (`LocalTasks`, feature `local`) and keeps its own dependency on `fs-tasks-core` for the sheet and the fallback read; moving it to `RpcTasks` is open (below).

Version 0.6.0: on `fs-interfaces` v0.44.0 and `fs-objects` v0.4.0. New: `Error::Changed { id, now }` for a stale revision (typed; the client no longer reads `conflict:` from the text, the detail still starts with it), `Items.list` pages cut in the store after the id of the last event (was quadratic), `SupportReport.instance` from the identity of the store, `Items.occurrences` fills `damaged` and `cut` (a cut answer is sent shorter instead of refused), and problem extensions `id`, `kind`, `issue`, `size`, `limit` (table below). **Task moved out (ADR 0050).** `Task` is owned by `fs-tasks`; this repo has no Task model, validation, upgrade, queries or VTODO code any more.
The core of the calendar depends on **no task crate**: it shows tasks only through the trait `TasksInWindow`
(`CalendarRepo::with_tasks`, `agenda`) and hands the tasks of an import to `TaskIntake` (`with_task_intake`); `fs-calendar-tasks` puts the contract `tasks.capnp` behind them. `CalendarObject` (the Event-or-Task enum) is gone: the API takes `Event`.

The candidates are read from the store a page at a time, ordered by the event's own id kept as the index `page_key` (lower case and unique, so the store sorts and compares it alike; the cursor is `page_key > last`; the first page is one event, then as many as fit 16 MiB by the heaviest of the page before). Every event written by this version has a `page_key`; an event without one (written by v0.4.x) is named by an `Error::Stored` on every window until `upgrade_index` has rewritten it, and `fs-calendar-server` does that at its start. **Which cut is a cut:** one event that is too much for the window by itself (more than 10 000 instances, more than 65 535 starts in a range, or more than the answer budget less a reserve of 1 MiB) is **named alone** (`Damaged`, `cut: false`, its id, also on stderr) and the rest answers; a `cut` (`cut: true`, since 0.6.0 sent as `cut` and no longer as 413) is only what the good events together put over the budget of the answer. **Measured upper bound** of a question (`tests/memory_nodes.rs`, counting allocator; claimed: three times the answer budget plus three copies of the heaviest event, the store's own memory aside; the figures are the last run): objects of one entry (30 000, 23 MiB estimated) 44 MiB to write and 77 MiB to ask; chains of depth 10 39 and 80; 90 000 small numbers 10 and 37; 49 000 arrays of one element 14 and 41; 3 000 chains of arrays 14 and 42; 40 events of 10 000 small objects each, a month: 61 MiB; a master of 4 MB with 2000 overrides 41 and 28 (`tests/memory_overrides.rs`); a daily series of 150 years of a 20 KB event holds the budget (`tests/memory.rs`). **Not bounded by this crate:** `fs-objects` v0.2.0 keeps about 6 MiB for each distinct page query of rows this heavy (sixty queries of one row each hold 330 MiB, measured without this crate), so 40 events of 20 MiB estimated each, a month, take 169 MiB (the test adds 6 MiB per event for it); it is the store's memory, reported to the strategy (statements with the key or offset written into the SQL text, apparently kept). **Rules:** a rule whose one period can give more than 100 000 starts, or one without `count` and `until` that gives more than 320 starts a day (every five minutes are 288; every four are 360), is refused when written (`Error::RuleTooExpensive`, problem `calendar/rule-too-expensive`, 422). 320 a day are 9 920 instances in 31 days, below the 10 000 of one event, so a legal series without an end is not cut by the number of instances in a month window (tested for every five minutes: 8 928 instances); whether its instances fit the byte budget depends on the size of the event, and a series with an end or a `count` can still be too much for a window, which is then named. Nothing promises that every series that can be written can be answered for every window. When read, a window is walked **from its own start** only where that gives the same instances as walking from the series start: `daily` and `weekly` rules, and `hourly`, `minutely`, `secondly` rules **without any `BY` part**, all without `count` and without `bySetPosition`, and never behind the rule's `until` (the start is shifted by whole periods of the interval). The sub-daily rules with `BY` filters are not shifted because the engine aligns those to the day, not to the start (a minutely rule every 7 minutes in hours 2 and 3 gave other minutes from other windows), and `bySetPosition` depends on where the walk begins. `tests/jump.rs` compares 400 random rules and windows (fixed seed) and the two reported rules with the engine from the real start. `monthly`, `yearly` and every rule not shifted are walked from their real start, estimated at most 500 000 starts, and the engine itself stops after 500 000 dates (tested on the engine directly), so a sub-daily rule with `BY` parts that is allowed (up to 320 starts a day) becomes unanswerable after a few years and is then named alone. A rule the estimate or the engine refuses, and any event that is too much for the window by itself (older data included, also with an `until`), is **named alone**: one series never makes the rest of the calendar unanswerable. An edit of an event whose rule is unchanged is not refused when the end of its series cannot be computed: it is stored open-ended (a candidate for every window from its start) and checked at every read. A rule that never hits (`byMonth 2` with `byMonthDay 31`) ends by the engine's own bound, about 150 to 330 ms per event and question. ## Admin window `fs-calendar-app` (R1, v0.0.3)

The old workbench window (month/week/day/agenda over `fs-components-workbenches`, `RemoteCalendar`, import and export flags) is **gone from the build**; its code is in git at the tag `v0.0.2` (and branch `main` before the merge of `r1-admin`). Import and export are the commands `fs-calendar import|export` of `fs-calendar-cli`, not rebuilt here. The window is the shell of ADR 0065 (`fs_components_app::AppWidget`) with two screens: **Calendar** (the component `fs-components-calendar-grid`: month, week, day) and **Events** (`fs_admin_frontend::AdminSurface`, generated from the `Event` description, in the style `Admin`). Menus Program / View / Help and About (`FreeSynergy.Calendar`, `v0.0.3` from `CARGO_PKG_VERSION`, licence, repository) as in `fs_admin_frontend::window`. No `blinc_*` import, no render code. In process, like before: `fs-calendar app [--store FILE] [--zone Area/City] [--size WxH] [--snapshot PNG]`; default store `objects.db` in the data folder of the program (the file `fs-calendar serve` uses; two processes on one file are not supported).

## Problem extensions (RFC 9457)

The detail text stays as it was; what a client used to cut out of it is an extension (`coding.md` section 2a). Keys: `id`, `kind`, `issue`, `size`, `limit` of `fs-interfaces::rpc::problem_keys`.

| Core error | Problem type | Extensions |
|---|---|---|
| `NotFound(id)`, `Changed { id, .. }` | `calendar/not-found` 404, `calendar/conflict` 409 | `id`, `kind=event` |
| `Store(NotFound(id))` | `calendar/not-found` 404 | `id` |
| `Invalid(issues)` | `calendar/invalid` 422 | `issue`, once per issue |
| `Time`, `Recurrence`, `ICalendar` | `calendar/invalid` 422 | `kind` = `time`, `recurrence`, `icalendar`; `issue` = the reason without the prefix |
| `MediaType(m)` | `calendar/invalid` 422 | `kind=media-type`, `issue` = the media type |
| `Json`, a text that is not JSON for the event limits, `Store(Invalid)` | `calendar/invalid` 422 | `issue` |
| `RuleTooExpensive(why)` | `calendar/rule-too-expensive` 422 | `issue` |
| `TooLarge(n)` | `too-large` 413 | `size`, `limit` (`MAX_EVENT_BYTES`) |
| `TooHeavy`, `Limit` | `too-large` 413 | `issue` |
| an answer or a request above a page | `too-large` 413 | `size`, `limit` (by `fs-interfaces`) |

Tests: `fs-calendar-server/tests/facts.rs` over the socket, the rest in `src/facts.rs`.

## Decisions

* **Time handling.** `start` is a local date-time in `timeZone`; no `timeZone` = floating, interpreted in the repo's floating zone (default UTC, `with_floating_zone`).
  DST: an ambiguous local time takes the first occurrence, a nonexistent one uses the offset before the gap. `P1D` is a nominal day (25 h across the autumn change), `PT1H` is exact.
  `Instance` windows are half-open `[from, to)`; zero-length events count when `from <= start < to`.
* **Overrides.** Keys are local date-times in the master's zone. `{"excluded": true}` removes an instance; other patches use JSCalendar paths
  (`title`, `participants/p1/participationStatus`, `start`, `null` removes); a key the rule does not produce is an extra instance (RDATE-like).
* **Object id = uid** when the `uid` is a `urn:uuid:` UUIDv7. Re-imports skip known `uid`s (originals are immutable).
* **Tasks** (envelope, RFC 9253 / 10051, queries, VTODO) are decided and documented in `fs-tasks` (ADR 0050). The calendar's `agenda` asks `TasksInWindow::due_between` for the tasks due in the window.
* **ICS originals.** One file with several UIDs is split textually: header + all `VTIMEZONE`s + that UID's components + `END:VCALENDAR`, lines copied unchanged
  (so the original per object is exact text of the source, though not the whole file). A one-UID file is kept whole.
* **Reserved-in-2.0 properties** (`sendTo`, `replyTo`, `localizations`, iTIP scheduling properties) are **kept in place**, not moved to legacy: the demo data uses `sendTo`,
  and they are needed for invitations. Revisit when a scheduling extension exists.
* **Export fixups.** Participants get `calendarAddress` from `email` / `sendTo.imip`; participants with no address at all (e.g. the demo's "Project owner") are omitted from the
  ICS because calcard cannot express them (it even `debug_assert`s). The converter call is wrapped in `catch_unwind`.

## Open points

* **Question to the owner (provisional):** the shape of JSCalendar JSON on `exportText` for several events (JSON array now; a JSCalendar `Group` is the alternative). Reversible: the importer reads both.
* **`updateIf` and `Event.revision`** (`events.capnp`) are served: `Event.revision` is `Revision::of_text(updated, content)`, a 64-bit FNV-1a fingerprint, equal on every read until the event is written; `updateIf` calls `Calendar::update_checked`, a stale revision is `Error::Changed { id, now }`, on the wire `calendar/conflict` (409) with the extensions `id` and `kind=event` and a detail still starting `conflict:`, nothing is written; a client decides by the type and the extensions, not by the text. Atomic inside one server process only (the writes take turns), as the contract says.
* **`Items.occurrences` damage and cut (0.6.0, `events.capnp` v0.44.0):** `damaged` carries `(id, reason, key)` of the core `Damaged`, `key` empty for a whole event. `cut` is true when any core `Damaged.cut` is, and the core sets it for every entry whose reason starts with `cut: `: what the good events together put over the answer budget **and** one event that is too much for the window by itself (more than 10 000 instances, more than 65 535 starts in a range, or more than the budget less its reserve), as the contract says. An event whose rule cannot be walked from the window (the walk bound, reason `recurrence: …`) or whose override does not read is damage with `cut = false`: it is missing, not cut. At most `MAX_DAMAGED` (1 000) entries are written; if there are more, one more entry (the id of the first left out, reason `… and N more not listed`) says how many; the bytes of the listed names count into the size of the answer. Damage is also said on stderr (the same entries). The app (`fs-calendar-app`) reads the core's `Window` directly, does not look at `cut`, and treats a non-empty `damaged` as a failed reading as before: nothing new breaks, and since an event cut alone was in `damaged` before, the set of cases does not change.
* **Writing many overrides is slow:** the check of the overrides (`validate/overrides.rs`) copies the master once per override, so 2 MiB with 20 000 overrides takes about 3 s under the write lock. Not changed.
* **Memory of writing** (measured by the review, not bounded here): a 15 MB text costs about 165 MiB to write, four at once about 660 MiB; an import of 2 MB with 15 000 events 127 MiB.
* **Module heads and a text comparison:** `model/counter.rs` says `none` because it is a mutable counter that also checks the limits (no pattern of coding.md section 2 describes that); `model/bounded.rs` recognises its own refusal by the text of the serde error (`split_once(MARK)`), which coding.md section 2a does not allow and should become a typed error.
* **Fail open for older data:** an event whose rule could not be written today is named alone when its window is too long (`cut: true` since 0.6.0, reason `cut: …`), not a `too-large` for everyone; an edit that leaves the rule alone (a new title) is not refused for it; `migrate_time_fields` does not check the rule (it can still stop at `TooHeavy`).
* **Small differences, not changed:** the depth is counted one level apart by `parse_bounded` and `build` (both answer 413); monthly and yearly rules are never shifted, so a dense allowed monthly rule is named after about three years; (the pages of candidates are read by `page_key` since 0.5.0).
* **Old data above the limits:** an event stored before the limits (more than 40 MiB estimated) is read as before, but `update` of it answers `TooHeavy`; `upgrade_index` names such an event in its report and goes on with the others.
* **`count` beyond 65 535 of a sub-daily rule cannot be written** (its end cannot be computed in one range): `Error::Limit` at write, which used to be a plain recurrence error.
* **Unknown `TZID` is refused, not stored with a note** (provisional, easy to reverse): storing the event at the wrong time was the fault; a note beside a wrong time is still a wrong time.
* **`privacy` alone does not reach the envelope**: only the marking `freesynergy.net:sensitive` does. `CLASS:PRIVATE` events must stay storable in an unencrypted store. The frontend still treats `private` / `secret` as marked for its own export.
* **Module heads** use the names of coding.md section 2 as it stands since 2026-11-07 (Specification, Value object, Visitor, Constants are in it now); a test file names what it tests.
* **`normalise_uid` exists here and in `fs-people-core`** (same rule): it belongs in a shared crate (coding.md section 4), for example `fs-jscalendar`.
* **`Registry` / `Subscription` exist here and in `fs-tasks-core` and `fs-people-core`**: a generic one belongs in `fs-interfaces::rpc` or `fs-objects`.
* **`fs-calendar-server` has no `--tasks-socket`:** tasks in an imported file are noted as "not imported", not stored. `RpcTasks` (`fs-calendar-tasks`) is the client that would attach one (`with_tasks` and `with_task_intake`); the option and its test are not written.
* **The app holds the task store in its process** (`LocalTasks`) and reads tasks with `fs-tasks-core` types; it should use `RpcTasks` and the JSCalendar text.
* **`DueTask` is read from the first page to the last**: `RpcTasks::due_between` follows the cursor until it is empty and fails as a whole if one task is too large for a message (`too-large` carries a cursor past it; it is not used). A window with very many tasks is held whole.
* **`tests/counting.rs` of the core may be unreliable:** it uses global counters of an allocator, which parallel tests in one binary share. The row counter of the server (`tests/counting.rs` there) is per test and does not have the fault.
* **The order of `Items.list` is by id now** (the key the pages are cut at), no longer by first start; ids are time ordered, so it is nearly the order of creation. `Calendar::list_events` (used by the app) is still by start. An event written before `page_key` existed (v0.4.x) is not left out silently: the first page of `list_page` and every `window`/`occurrences` fail with `Error::Stored` ("N of M events have no place in the order … run upgrade_index") until `CalendarRepo::upgrade_index` has completed the index. **`fs-calendar-server` runs it at its start** (idempotent; the number rewritten and each event that could not be repaired go to stderr; an event that cannot be repaired keeps the pages and windows failing with that message, it is never skipped). A library user calls `upgrade_index` after opening the store. Tested with a database written by the code of tag v0.4.1 (`fs-calendar-core/tests/fixtures/v041.db`), in the core and with the real program (`fs-calendar-server/tests/binary_old_data.rs`).
* **`agenda` is no wire method;** its task query is one range query of the task provider, not paged. `occurrences`/`window` read their candidates by `page_key` since 0.5.0 and are linear (measured with the row counter: 80 events 80 rows, 160 events 160 rows).
* A start must be in years 1 to 9998 (`limits::FIRST_YEAR`, `LAST_YEAR`): the time library saturates at the edges of years 0 and 9999, so an event there would silently move.
* A series is expanded at most `MAX_INSTANCES_PER_EVENT` instances per question; the rule is walked at most `MAX_RULE_STEPS` steps from its start. A cheaper way would shift `DTSTART` by whole periods for daily and weekly rules (not done: `COUNT` and the `BY` rules depend on the real start).
* `agenda`, `upcoming`, `migrate_time_fields` and `get_event` are not in the contract; they stay on the trait as local helpers and use the nearest capability id.
* tzdb is picked once per process (first use); a system tzdata update needs a restart. Stored originals keep the version they were imported with, nothing is re-evaluated against a newer one.
* Objects written before fs-objects 0.2 or before v0.5.0 need `upgrade_index()` once (the store migration cannot compute their envelope times or `page_key`); `migrate_time_fields()` is that, with only the number. The server program does it at every start. Each page or window checks with two `count` queries that no event lacks its place.
* Wall-clock recurrence: a start in a DST gap is not skipped (RFC 5545 allows either) but moved by the offset before the gap, as for single events.
* Per-instance invitation replies (an `Accept` for one occurrence only) are not modelled: `respond` changes the master's participant.
* Recurrence with `rscale` other than gregorian is refused with an error. `firstDayOfWeek`, `skip` are passed through partly (`WKST` yes, `skip` no).
* Alerts, `locations`, `virtualLocations`, `links` are preserved but not typed or interpreted.
* No scheduling/iTIP transport (`METHOD:REQUEST` etc.), no CalDAV; free/busy computation is not implemented.
* The ICS export is as good as calcard's; vendor properties become `JSPROP` lines (RFC 9554 style) and are not understood by other clients.

**Taken uid and conflicts (fs-tasks v0.9.0).** `Error::Exists(id)` (a task has the `uid`) is `Forwarded::Skipped` in `LocalTasks`; over RPC a `tasks/conflict` problem with the extension `id` is `Skipped`. Any other conflict (a UUID `uid` that is the id of an event in a shared store, `an object with id X exists`) is `Forwarded::Refused` for that task: it is not "already known" and is not stored. Tested through both adapters (`tests/local.rs`, `tests/rpc.rs`). Over RPC the tell is the extension `id`; an older server without it would make every conflict a refusal.
